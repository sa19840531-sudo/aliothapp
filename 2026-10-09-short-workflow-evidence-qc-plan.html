01 / ASSESSMENT结论与方案取舍

四项思路均合理、可实施，且能沿现有架构增量建设。短流程应定义业务目标、可观测检查点、必须满足的因果关系和退出条件；实际入口、页面数量、按钮形式及中间操作可以变化。证据、规则适用性与结果仍需严格核验，缺证、业务缺陷与技术失败分别处理。

方向判断建议补充
增加短流程 Workflow Skills合理。可以提高探索目标性与取证一致性。Skill 提供多种入口、交互策略和取证方法；Journey 合同描述业务检查点与证据义务；Explorer 自适应规划路径，工具与策略校验每次动作。
流程证据同目录、编号命名合理，利于审查、对照与下载。以 Journey Execution 为证据组边界；目录从 Manifest 和证据关联记录生成。保存步骤、尝试、动作、采集、时间、制品哈希，禁止仅凭文件名还原流程。
规则由页面类型扩展到短流程必要。页面类型无法表达跨页动作和结果。新增页面 / 流程 / 任务三类匹配目标；将“匹配对象”和“证据输入范围”拆开。流程规则按稳定流程类型及场景匹配，页面类型可辅助找入口。
使用一系列流程证据判定必要，但不能把图集数量或预设动作数量作为完整性标准。把真实动作、采样和检查点形成 Observation，按规则的证据义务、角色、因果关系及业务不变量选择输入。截图、DOM、UI Tree 继续作为原始依据。

执行完整性

目标检查点是否采证或明确记录阻断，必需场景是否处理，真实动作与终态是否可追溯，探索上下文是否恢复。

证据充分性

是否保存规则所需的前后态、时序观察和同源身份，能否从原始制品复核。

产品合格性

暂停、拖动、支付取消等行为是否符合规则。操作成功完成取证也可能得到产品不合格结论。

范围控制

“完整播放器流程”应解释为所选业务检查点及适用场景的证据完整覆盖。产品自动播放、先选择剧集、先关闭广告或进入全屏后显示控件，均可以形成有效路径。首期明确必需目标和探索预算，不承诺穷举所有组合。支付首期覆盖允许的只读展示与安全导航；沙箱结果和权益核对作为后续独立能力。

推荐通用探索采用目标驱动与动态路径；经验证的产品脚本可以作为可选快捷策略，运行前核对条件，失配后回到通用探索。新产品不以编写专属脚本为默认前置条件；平台能力不足或高风险动作仍需要明确适配与授权。

03 / DOMAIN领域模型与职责边界

前端称“短流程 / 流程”，领域统一使用现有 Journey。Workflow Skill 是策略指导；JourneyDefinition 是业务检查点与证据合同；ExecutionPlan 冻结合同和自适应策略；JourneyExecution 保存一次真实探索。业务检查点与具体动作是两层对象：一个检查点可以通过多次导航和操作取证，一份可信观察也可以服务多个检查点。

实体 / 合同关键身份与内容建设方式
JourneyDefinition / Versiondefinition_id、version、content_hash；flow_type、scenario_key、业务检查点、证据义务、必要因果依赖、退出与恢复合同。扩展现有定义协议；不写产品按钮名称、固定页面路由或全局线性动作表。发布后不可覆盖。
ExecutionPlan / PlanRevisiontask_id、source_agent_run_id、合同版本、场景、参数指纹、规则需求、策略快照；局部动作计划修订及前态依据。解除单计划限制。合同与边界冻结，运行路径追加修订；不修改已发生动作。
JourneyExecutionexecution_id、execution_plan_id、执行轮次、Session/Surface 段、入口与出口、业务上下文。复用现有执行记录；重跑新实例，不混合上次成功步骤。
CheckpointAttempt 提案checkpoint_id、attempt_id、证据义务、尝试目的、实际观察、阻断、关联动态动作列表。新增检查点尝试语义；其 observed 表示材料已观察，不能表示产品符合预期。
StepAttempt / Action Trace动态 step_id、真实事件序号、attempt_no、意图及回执、source/result_capture、起止时间、错误。保留现有具体动作尝试。检查点和动作使用显式关联，不能把 next_step_index 直接当业务覆盖游标。
JourneyEvidenceLink 提案execution_id、checkpoint_id、checkpoint_attempt_id、trace_event_id、具体动作 / 步骤引用、Capture 与 Manifest、角色、采样时间。支持检查点与事实多对多关联；观察类材料可无新动作，动作规则必须有相应真实动作身份。
EvidenceInputSet规则合同、目标实例、输入版本、成员顺序、Manifest / Artifact 引用、候选快照哈希。复用封存机制；新增检查点选择与证据闭包，数量由具体合同决定，不用目录或固定帧数替代充分性。
JourneyObservation 提案原始证据引用、步骤观察、转移、缺口、能力事实、断言支持与冲突。从冻结 InputSet 生成规则判定投影，可缓存但不能成为独立事实源。

责任分工

QcOrchestrator：统一管理任务状态、预算、租约、补采、完成门禁和报告绑定。现有 Explorer：根据当前观察、未满足证据义务与 Skill，动态选择检查点及合法动作。JourneyRunner 自适应模式：维护检查点覆盖、局部计划修订与真实动作尝试，校验依赖并持久化。Driver / Broker：校验权限、表面、目标及回执。Publisher / RuleJudge：核验证据、发布工作项并判断产品行为。新增能力属于 Journey 的局部运行模式，任务最终状态仍由原 Orchestrator 管理。

04 / PIPELINE整体执行链与双重适用性

  1. 冻结目标、证据义务与运行边界

    从规则版本生成流程类型、场景、必需业务检查点、证据合同和必要依赖；运行策略提供动作与预算。未预先固定入口页面及点击顺序。

  2. 发现入口并核对运行能力

    结合真实 Capture、账号与产品能力、当前表面状态核对入口。发现播放器可作为触发线索；最终按目标流程和上下文核验。记录适用 / 不适用 / 未证明。

  3. 动态规划与逐动作观察

    观察当前状态 → 检查可复用证据 → 选择尚缺检查点及下一动作 → 权限校验 → 正式执行 → 留证 → 更新覆盖。必要时改变入口、插入清障、换策略或重规划；同一 Session 仍保持单写者。

  4. 绑定真实路径与检查点证据

    每次正式动作和观察提交后，按规则要求关联检查点尝试。记录路径分支、局部计划修订、时序与因果关系；保存失败、未知和中止材料，不仅保存成功路径。

  5. 按流程匹配规则并判定

    流程目标产生独立候选；按每条规则选择最小充分证据，生成冻结 InputSet 与 JourneyObservation，经确定性断言 / 模型复核进入原有 RuleJudge 写回链。

  6. 补采、复核、覆盖与完成门禁

    缺证进入可恢复补证请求；不可靠模型结论进入复核。流程终态、规则工作项、未决请求和报告绑定均收口后，由既有 Orchestrator 决定最终状态。

适用性与执行可行性必须分开

产品是否具有该流程

会员产品有支付链路，即使平台禁止真实下单，支付成功规则仍可能业务适用。功能入口未找到、账号不满足、页型未知不能直接推断不存在。

当前运行能否采足证据

设备缺媒体状态、没有沙箱支付权限、登录会话失效等属于运行能力或取证约束。记录阻断原因，保留待判规则与真实缺口。

流程完成后核对返回页面、账号、媒体或购物上下文。无法恢复时记录 return_context_unverified，交现有恢复流程；不直接继续点击下一入口并遗失探索状态。

05 / ADAPTIVE CONTRACT业务检查点合同、Workflow Skills 与产品适配

DSL 作为声明式合同，定义要观察和判断的业务行为，不预写一串产品页面与控件操作。首期可采用受校验的 JSON 表达，不必建设复杂脚本语言。增加 player-interaction-workflow 与 payment-readonly-workflow 提供策略；现有 Explorer 负责现场发现和路径选择。

松绑范围：入口位置、页面数量、控件文案、菜单展开、导航、清障、等待与下一目标选择可动态变化。业务预期、证据来源、必要因果关系、权限及预算继续由冻结合同约束。
层稳定内容允许变化
业务检查点合同暂停尝试及其后观察、恢复尝试及其后观察；证据义务和必要依赖。如何进入播放器、如何显示控件、用哪些合法动作完成取证。
Workflow Skill语义识别、取证规程、失败处理、典型候选策略。策略选择、组合和局部替换；示例路径不是必经流程。
产品 / 平台适配当前状态证明、目标定位、动作能力与可观测来源。按钮、手势、原生控件或 Web 媒体操作；可选产品快捷路径。
实际运行路径真实动作与回执、前后采集、计划修订、关联及错误均持久化。节点数和顺序可以变化，但须满足规则明确要求的局部因果关系。
运行策略与规则标准权限、预算、采样合同、数值容差、业务预期和复核政策。在允许配额内分配局部动作与等待成本；不能由模型降低标准或扩大权限。

业务检查点不是页面状态的成功门禁

“暂停效果”检查点表示已尝试暂停并取得其后观察。观察到进度仍推进时，该检查点的证据可以充分，产品行为判为 fail。pending / observed / blocked / unresolved 描述采证处理状态；产品是否支持某能力与证据是否充分独立保存，不把按钮点击成功、期望页面到达或期望状态实现作为发布前提。

产品适配：通用策略优先，专属策略可选

  1. 语义能力：发现“播放 / 暂停 / 恢复 / 展示价格”等业务意图与当前状态，不依赖固定 page_type 或页面路由。业务能力、运行端动作能力、观测能力和授权状态分别核对。
  2. 实际目标：Driver adapter 从当前可信 DOM、UI Tree 或视觉候选定位控件，绑定真实几何和表面。存在多个候选时先观察或消歧；不能用旧坐标硬点。
  3. 策略候选：可通过菜单、点击画面、全屏、返回入口等合法路径取得证据；策略变化写入计划修订。无法证明目标或效果时记录未知，不猜测成功。
  4. 可选产品配置：表达已知入口别名、观测源、业务上下文提取和安全返回方法；只有反复出现的差异才形成适配。已有脚本须验证前态，不匹配时回到通用探索。
  5. 合同一致性：不同产品可以选择等效观测源，但该替代必须经合同允许并满足精度；模型不能把画面变化自动当作精确播放进度，或删除不易完成的检查点。

版本与分支

冻结 Skill、合同、策略、工具能力及规则版本；运行时产生的路径和局部计划修订追加留存，无需为每次点击路线发布新的 JourneyDefinition。scenario_key 表达业务行为目标，例如暂停恢复或只读价格核对，不表达产品页面组合。

必需场景来自冻结规则范围，可选能力按真实发现记录。意外广告、登录墙、内容失效等形成实际分支与缺口；模型不能为提高覆盖率删减目标。新发现会影响适用性的能力按版本化事实台账与既有门禁裁定处理，不静默缩小原分母。首期支持局部重规划及有限因果依赖，无需建设通用嵌套工作流引擎。

Skill 经草稿、回放验证、发布和停用管理，正文加载当前业务目标和候选策略，参考材料按需读取。Skill 提供指导，合同与正式动作接口提供可验证边界。

06 / RUNTIME自适应调度、预算与恢复

目标驱动的观察—规划—执行循环

每个 Run 从冻结规则需求生成待探索流程清单。发现入口后，先扣专项预算、核对能力，再创建计划和执行实例。优先级由业务规则严重度、证据缺口、当前入口可达性和剩余成本决定；相同内容 / 商品 / 场景通过业务参数指纹去重。

普通页面遍历继续存在。流程执行期间持有当前 Session 的动作租约，探索导航暂停；流程完成或明确中止后回到原遍历游标。不同 Session 可以并行，已封存证据的离线分析及 RuleJudge 可以并行，同一浏览器 / 设备保持单写者。

  1. 观察并复用已存在的可信材料

    识别当前业务对象、账号、表面、阻挡及能力，检查已有 Capture 是否满足检查点。只读事实可以复用；要求特定动作效果的规则仍须真实动作与因果关系。

  2. 选择可达的检查点与局部路径

    从尚缺证据中选择满足必要依赖的目标，结合 Skill、当前候选和运行策略规划下一动作或短动作块。没有必要依赖的检查点可重排。

  3. 校验动作并提交实际结果

    核对权限、租约、当前目标和预算；执行一次正式动作并采集回执及所需材料。不能将一次模型建议中的多个点击无观察地连续下发。

  4. 更新检查点、调整策略或结束

    保存实际观察、缺口与冲突。可以换候选入口、补充观察、处理阻挡、重规划或明确中止。充分失败证据立即交判，不反复尝试把产品改成成功状态。

每次局部计划记录 revision_id / parent_revision_id / source_capture_id / checkpoint_id、策略来源、简短结构化选择理由、预期采证对象与实际结果。持久化事实支持恢复，不要求模型复现相同措辞或重新猜测旧路径；任务控制仍由现有 Orchestrator 完成。

约束建议首期策略审计要求
任务预算专项动作、等待时长和制品配额计入全局预算；可配置保留额度，避免页面遍历耗尽所有流程预算。记录预留、实际消耗与未覆盖项。预算耗尽是未完成原因。
尝试与策略切换按当前状态选择合法替代路径；相同目标无变化时限制重复，转向观察、其他候选或中止。有副作用动作超时先查回执与状态。检查点、具体动作尝试、策略修订、错误类型、切换理由及是否已执行。
租约失效丢失租约立即停止动作；由现有恢复所有者接管，不另起并行执行器。owner、token、epoch 与版本，旧所有者写回必须被拒绝。
采集失败动作回执已成功时，优先恢复同次采集上传 / 关联；不能重做动作以“补一张截图”。区分动作、采集、上传、提交和关联阶段。
页面与路径变化每个动作前核对可信 Capture；出现弹层、路由变化、隐藏控件或新入口时重新规划。合理路径差异不直接判失败。新观察、局部计划修订、正式清障和真实目标；采集不能偷偷唤醒控件。
恢复策略按缺证合同和当前状态选择恢复上传、继续取证、返回可证明的安全状态或新实例重跑；核验不变量，非重放场景人工或中止。恢复决策依据、父实例、业务身份、因果连续性、禁止复用片段及新输入版本。

三个独立状态维度

执行状态

planned / running / completed / aborted / failed / cancelled。表示执行器是否完成采证工作，沿用或扩展既有枚举。

证据状态

collecting / sealed_sufficient / sealed_partial / rejected_integrity。按具体规则计算充分性，同一流程可能只对部分规则充分。

业务判定

pass / fail / evidence_insufficient / manual_review 等沿用规则结果。不得将 Runner 的 completed 直接映射为 pass。

保留失败证据：点击暂停后进度仍增加，是应交给 Judge 的潜在产品缺陷；不能因为步骤“未达到期望播放态”就抛弃流程。执行器只检查可观测性、技术边界与退出条件；业务期望由规则判断。

Microsoft Agent Framework 有工作流检查点能力，可辅助模型执行状态恢复；浏览器、设备和服务端交易状态仍要独立核验。本仓库固定 agent-framework-core==1.10.0，不能直接套用新版文档 API。建议先复用现有 PostgreSQL 游标、租约与 StepAttempt，新增 MAF 检查点适配时单独验证版本兼容。[E1] Microsoft 官方检查点说明

顺序、时间和连续性

  • 顺序：真实事件先后与持久化追加顺序分别记录；以事件序号、动作回执、采集时间及因果边核对。保留 attempt_no / sample_index；step_index 仅为旧模式或展示信息，不能要求所有产品执行同一全局顺序。上传与文件排序不能替代动作发生顺序。
  • 时间：记录采集开始 / 结束、设备观察时间、服务端接收时间及同段单调偏移。跨设备注明时钟偏差；不能仅凭两张图片的秒级文件时间判断短时变化。
  • 因果：动作前后帧指向同一次正式动作与检查点尝试；只核验规则要求的局部依赖。暂停观察窗口必须在暂停尝试之后，并证明未换媒体或插入破坏观测的动作；其他无依赖的检查点允许调换顺序。
  • 同源：冻结集合按同一源 Run 校验。跨 App、浏览器或支付提供方的合法切换用明确 segment 与受控转移回执连接，不强求同一 Session，也不允许任意跨会话拼图。
  • Epoch：区分原 Capture 的采集 epoch、补证归属和最终封存 epoch。封存提升不能要求重写原 Capture 身份；通过现有合法血缘与 InputSet 合同核验。
  • 重复：相同像素哈希可以代表不同真实时间采样，保留独立 Capture 的时间和来源；展示可去重，但不能将重复图片当作状态变化。

匹配算法

  1. 冻结候选：规则清单按 target 分组；页面规则走原候选链，流程规则走独立流程候选链，不进入页面类型必填过滤。
  2. 核对业务适用：用产品声明、实际入口 / 能力观察、账号条件形成适用性快照。not_applicable 必须有明确、可引用依据。
  3. 核对流程实例：flow_type、scenario、业务参数、渠道和定义兼容性满足目标后绑定 execution_id。页型未知不自动排除已可信确认的流程实例。
  4. 核对输入就绪：按 required_checkpoints / required_evidence / relations / observations 检查证据。实际页面、导航次数和非必要操作顺序变化不影响匹配；两张图或 completed 不能自动放行。
  5. 发布工作：冻结 InputSet 和目标合同，幂等创建原有 Inspection Work；受影响规则按目标实例去重。
情形处理避免误判
产品明确没有该功能有权威声明 / 可验证负向探索依据时记 not_applicable。找不到入口不等于功能不存在。
有功能，未到达入口适用或未证明；继续探索或记录覆盖缺口。不能记 skipped 后计为覆盖完成。
页型不确定，流程入口与业务身份可信可以形成流程候选；按流程合同继续核验。避免流程判定继续被 page_type 兜底拦截。
现有端缺必要动作 / 可观测字段记录运行能力阻断及证据不足；必要时按规则政策人工复核。能力缺失不能改为业务不适用。
流程未完成，但已存在充分失败证据仅受该证据覆盖的断言可得到 fail，其余仍缺证。不要求产品操作成功才交给 Judge。

执行身份与统计

建议工作幂等身份包含 source_run + rule_contract_hash + target_instance_id + input_set_hash，同时保持现有 lease / attempt / 幂等写回。页面、流程、任务结果采用显式目标字段；流程结果可以无 page_capture_id，但必须有 journey_execution_id 和 InputSet，禁止随机选一页作为宿主。

一条规则可能针对多次流程实例执行。界面分别统计唯一规则覆盖数与实例执行数；任务级合成按冻结规则聚合政策处理，不能默认“最后一次覆盖前一次失败”或“任何一次通过即可通过”。首期可采用任一实例失败则该规则失败、必需实例缺证则未完备的明确政策。

09 / JUDGING成组证据判定：真实路径与业务检查点

流程图集保存完整探索材料；每条规则消费其最小充分子集。EvidenceInputSet 先冻结该规则的权威选择快照，再按快照完整成员封存。不得在冻结集合后让模型挑选有利图片，也不把流程所有制品无差别塞进上下文。

  1. 可信与完整性校验

    目标、Run、段、Capture、Manifest 精确身份与哈希、角色、附件闭包及合法血缘均通过。完整性失配进入拒绝输入 / 技术处置，不能作为 pass 或产品 fail。

  2. 检查点事实投影

    把实际事件映射为检查点的证据集合，保留正式动作、前后态、采样时间、局部因果与缺口。不同产品路径可满足同一合同；OCR / Vision注明来源与不确定性。

  3. 确定性断言优先

    对顺序、样本数、时长、进度变化、价格关系、订单标识和状态比较使用合同中的精确规则；缺字段不补默认值，测量误差按合同处理。

  4. 语义判断与复核

    对提示、弹层、视觉反馈等非确定性内容调用模型，输入为冻结的检查点事实及真实引用；不能因路径不同判失败。冲突、低置信和 Provider 故障沿既有复核政策收口。

  5. 结构化写回

    逐断言记录 outcome、observed、expected_ref、evidence_refs、缺口及冲突；继续使用原有 RuleExecution、人审、报告和 Completion Gate 链。

10 / PLAYER播放器：跨产品检查点与实际分支

以下是业务能力与证据关注项，不是所有产品必经的页面或动作顺序。Explorer 可从内嵌播放器、详情、短剧、选集或已有播放状态切入，按当前控件和规则需求选择路径。Web/H5 复用现有媒体与 sequence；App 先补齐可信动作和观测，再声明相应覆盖。

返回与再次进入真实返回动作、来源上下文、重新进入的内容及进度。规则明确要求时检查记忆播放位置；位置容差和自动播放期望均由合同指定。

产品差异与实际分支

登录墙、付费解锁、广告插入、控件隐藏、手势操作与内容失效均按实际观察形成分支。可按策略正式清障、显示控件、换可验证入口或记录阻断；不要求它们先出现在 DSL 的节点表里。需要业务故障注入时另行声明运行能力，不将当前 network_fault stub 当可用。

操作存在但不生效应保留失败证据；仅未找到入口不足以判功能不支持。一次探索可以覆盖多个检查点，规则只取对应材料。倍速、清晰度、全屏等无因果依赖的关注项可按当前可达性重排；暂停观察必须发生在对应暂停尝试之后。

证据关注项示意：

player.interaction / pause_resume

  • 暂停尝试真实动作及前后材料按钮、菜单或手势由当前产品和运行能力决定。
  • 暂停效果尝试后的连续观察保留暂停失效；图标切换仅为辅助。
  • 恢复尝试同一媒体的正式动作根据当前实际状态选择策略，不伪造状态切换。
  • 恢复效果规则所需观察窗口验证推进或异常，因果绑定到本次尝试。
  • 退出上下文真实路径及返回依据按来源选择退出方法，不指定必须返回某个页面。

payment.checkout / readonly

  • 业务身份商品 / 方案、金额及账号态从当前真实展示核验，不假定固定入口。
  • 可比价格规则要求的位置与条件允许会员页、付费层或收银台，按实际产品映射。
  • 条款与渠道期限、币种及可见选择项按规则取证，不主动提交订单。
  • 动作边界真实控件、策略及阻断创建订单或扣款不能因路径重规划被绕过。

App 能力门槛

原生播放器可能没有可读 currentTime。后续可建设可信媒体状态、可验证时间码与 OCR 多帧、受控视觉观测等替代来源，并记录精度与可证明范围；当前 Android ocr_text 为 unsupported，不能直接依赖此采集能力，新增方案须实现并登记后启用。截图画面变化通常不能精确证明进度或倍速。所选正式动作与观测源未受能力登记支持，或精度不满足合同，才构成该路径阻断；未来经验证的进度条手势适配可作为 seek 的等效路径，不强求所有端使用同名操作。

11 / PAYMENT支付：区分只读链、沙箱交易与真实业务结果

场景业务目标与材料可以证明不能证明

12 / RECOVERY & GATE补采、重判与完成门禁

补采按检查点的证据缺口发起

EvidenceRequest 声明目标 JourneyExecution、checkpoint / attempt、缺失事实、角色 / 时间窗、因果约束、不变量及恢复边界，不指定必须点击哪个产品按钮。Explorer 根据现场选择合法补证路径，Orchestrator 管理调度；Judge 不直接操作设备。

缺口恢复方案输入版本
已有原图，上传 / 关联失败读取同次 Capture 和制品并校验，恢复提交与关联；不重做操作。补齐同次流程的真实关联后创建新封存集合。
当前同源暂停窗口少一个样本仅在现场连续性和所需时序仍成立时采样；不能事后伪造原时间窗。保留原版，新增完整窗口或新尝试的 InputSet。
设备已退出，暂停后证据丢失先核对能否恢复同次连续性；不能证明则新建实例，动态选择入口重取该检查点及必要依赖，不能接到旧暂停动作后。新 execution_id、新 InputSet，保留父实例与恢复依据；无需复现上次完全相同的页面路线。
订单 / 凭证 / 价格已变化按 exact 或人工政策处理；不以视觉相似判断状态等价。不得把新订单截图补入旧交易链。
模型故障或结论冲突沿既有重试与人工复核策略处理。无需补采时直接重判冻结证据。同 InputSet 可产生新 Judge Attempt，保留全部历史。

重判与不可变历史

规则、技能、模型升级后可对已保留流程证据独立重判；新规则需求超出历史证据时明确缺证。原始 Manifest、InputSet、执行结果和人审记录保持不可变，新结果通过 source_input_set、supersedes / parent 等关系连接。当前页面 journey_steps 仅为上下文，不能自动升格成已验证的流程主证据。

完成门禁扩展

  1. 本 Run 的必需流程范围已冻结，业务适用性为 applicable / not_applicable / unproven，负向结论有权威证据。
  2. 所有必需流程实例已技术终结，未完成分支和恢复失败如实列入覆盖缺口；没有未处理动作或采集。
  3. 流程证据封存和完整性核验完成；每条规则有可信输入或结构化缺证原因。
  4. 适用流程规则的 Inspection Work 已终结，EvidenceRequest 为完成 / 不可执行 / 过期等明确状态，无静默遗失。
  5. 人工复核政策、规则结果与报告身份满足既有 Gate；未证明的流程不能被“页面覆盖率 100%”遮蔽。

区分任务已终结与质检范围完整。含缺证任务可根据既有政策生成明确未完备的报告或预览，不能以放宽 Gate 获得完整结论。产品有明确 fail 不妨碍形成“证据充分的完整质检报告”。

覆盖指标

分别展示适用性、业务检查点证据覆盖、规则要求的因果关系覆盖、唯一规则覆盖、实例结果与未决补证。实际动作 / 导航数量单独展示，不作为覆盖分母。分母来自冻结合同及合法裁定的不适用项；新发现及范围修订有审计，不能靠删除困难检查点提高覆盖率。

所有流程日志、OCR、HAR、录屏与订单信息受任务证据权限约束。凭证不进入截图名称、模型 Prompt 或日志；敏感原始证据若确需保存，使用既有受限存储与保留策略，普通查看提供有来源关系的脱敏派生版本。保留查看、导出、补证、重判和人工改判审计。

前端复用现有规则表单、截图查看器、任务详情和权限守卫。首期新增详情分区即可；流程定义管理若采用独立路由，需同步管理端与部门端菜单、路由、权限及深链恢复。

14 / ENGINEERING兼容迁移与工程拆分

需要数据库迁移

  1. 规则目标：增加目标类型和配置，冻结匹配合同。旧规则保持原路径；已存在 task / matrix / Web sequence 特化输入不得仅凭空页型被自动转换目标。
  2. 多计划：执行计划扩展 Run、场景及业务参数身份，迁移 UNIQUE(task_id) 为经核对的新唯一约束。建议新身份为 task + source_run + definition + scenario + parameters_hash，定义版本作为冻结内容；旧计划保留可读且不被重写。
  3. 检查点与真实动作：增加 CheckpointAttempt、PlanRevision 及证据关联；复用 StepAttempt 记录具体动作，并建立检查点、动作、Capture 的同源和幂等约束。
  4. 流程目标执行：Inspection Work / RuleExecution / 补采请求及报告投影扩展 target_instance / Journey 引用，不能伪造 page_capture_id 适配旧表。
  5. 输入协议：冻结检查点证据与必要因果关系，成员数量和观测源按具体合同校验，实际路径独立追加；新增协议版本处理该语义，历史 v1 InputSet 的两 Capture 等约束仍按原规则验证。

扩展 → 回填 → 影子验证 → 逐步启用

顺序 Runner 的兼容：保留现有 linear 模式和旧合同，新增 adaptive 模式。后者从未满足证据义务选择目标，局部动作块可复用原处理器，但覆盖游标、依赖及动态尝试需扩展；不能仅把 steps 字段改名后声称具备自适应能力。验证过的固定脚本作为候选策略执行，失配时按策略返回动态探索。

先新增可空字段及新协议适配；回填只处理身份明确、可验证的数据，旧 Journey 无步骤绑定时标为 legacy_context，不能从页面时间线自动拼成“完整流程”。规则更新创建新合同版本，在途 Run 保持原快照；历史结果继续由原版本解释。

保留 feature flag：多流程调度、Journey 证据封存、流程目标规则、通用流程 Judge 分开控制。影子阶段只生成候选、完整性结果及对照结论，不改正式报告或 Gate。启用后遇到故障可关闭新调度与规则发布，已创建工作项按明确政策收口，不能静默丢弃。

15 / DELIVERY交付阶段与验收标准

以能力闸门推进，不以“Prompt 已增加”“接口返回 202”或“能看到多图”作为完成。建议先形成一个端的最小正式闭环，再扩展端和分支；三端共享领域合同，运行能力分别验收。

阶段交付内容准入下一阶段的条件
M0 · 合同与基准业务检查点 / 证据协议、必要依赖、自适应策略、多计划迁移、不同交互产品的样本。业务预期及边界清楚；合同不绑定页面 / 控件顺序；发布校验核对实际 Handler。
M1 · 跨产品播放器闭环同一暂停恢复 / 拖动合同，在自动播放、手动播放、遮挡或隐藏控件产品上运行：Explorer → adaptive Runner → 可信输入 → Judge / Gate。路径自动适配，新增导航合法留证；正确行为通过、错误行为失败、缺证不通过，不能因路径不同误判。
M2 · 流程规则与工作台页面 / 流程目标表单、适用性台账、多计划、流程时间线、导出与规则步骤引用。流程候选不依赖宿主页型；旧规则与 Web sequence 回归不漂移；多实例统计和权限正确。
M3 · App 与支付只读App 媒体动作 / 观测适配，支付展示链及返回，分支缺口与能力阻断。真实设备证明媒体时间、拖动及连续性；只读链无交易副作用，不把收银台到达计为支付成功。
M4 · 受控扩展步骤补证、重跑 / 重判、更多播放器分支、沙箱支付结果与异常。故障恢复及新输入版本闭环；沙箱业务标识与终态可信；高风险动作受正式策略约束。

最低验收矩阵

维度必测情况预期证据
跨产品适配自动 / 手动播放、不同入口与页面数、按钮 / 手势、隐藏控件、先选集、不同价格展示位置。同一业务合同形成不同真实路径；必需检查点与证据标准不变。新产品不要求先复制一套专属脚本。
局部重规划运行中出现广告、目标失效、菜单变化、候选歧义、路线恢复、无效果重复及能力未知。逐次观察、合法策略切换、计划修订及停止依据可追溯；不盲目重复，也不偷偷删检查点。
规则语义暂停失效、恢复失效、拖动错位、全屏无法退出；正确与错误对照样本。失败必须由真实动作与时间窗口支持，并定位到断言及制品。
流程完整性缺中间态、乱序、错误 attempt、换媒体、跨 Run、未记录操作、相同图重复。被拒绝或标注缺证，不能仅凭 completed / 两张图通过。
规则匹配页型未知但流程明确；存在入口却未到达；确无功能；运行能力不足。适用、不适用、未证明和能力阻断准确区分，覆盖分母有依据。
基础设施租约过期、进程重启、上传失败、重复事件、晚到 Capture、补证封存、取消。无重复动作或双写，步骤与工作项可恢复，所有历史版本可追溯。
支付价格不可比、导航创建订单风险、沙箱取消 / 失败 / 超时、成功 UI 但无业务终态。只读边界不绕过；沙箱单独标识；成功不能由截图文案推断。
工作台与报告不同流程图集无串图、步骤跳转、权限、窄屏、导出、旧结果、同规则多实例。可复核原图与引用，统计不重复，手机可读，无身份混淆。
兼容旧页面规则、三种已实现聚合策略、Web failure / interaction sequence、人审与 Gate。原合同继续有效；新增能力不改写历史正式结果。

建议验收指标

  • 至少覆盖三类不同交互产品，并用未参与适配的页面变体或新产品检验通用性；该数字是首期验收门槛建议，不代表现有结果。
  • 记录同合同跨产品检查点覆盖、通用策略采证完成情况、路径调整与人工接管原因，按业务能力差异分组，不用平均成功率隐藏缺口。
  • 目标实例、InputSet、检查点尝试、实际动作及原始证据身份完整率为 100%；错误关联、篡改及缺证样本不产生自动 pass。
  • 同 Session 保持单写者；合同 / Skill / 策略 / 模型版本和路径修订可追溯，目录可由清单重建。
  • 业务覆盖、证据充分、产品合格和动作成本分别计算；导航较长不直接判失败，成本仍受冻结运行策略约束。
实施优先顺序：先收口业务检查点与证据关系，扩展 Runner 的自适应模式，贯通正式探索、成组判定及门禁；以跨产品暂停恢复 / 拖动和支付只读核对为首批样板，再接工作台与导出。
