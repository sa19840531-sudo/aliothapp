## 只读事实与原因

1. 默认队列承载 App/H5，Web 使用专属队列，两个队列分别 FIFO。Worker 每个消费协程处理一个 Run，处理完成后才领取下一个；代码支持多个消费协程，没有强制全部任务串行的 Agent 限制。
2. 本轮读取真实线上 Worker 生效设置：默认 `ALIOTH_WORKER_CONCURRENCY=1`，Web `ALIOTH_WEB_WORKER_CONCURRENCY=1`，唯一存活实例角色为 `explorer,judge,web_explorer`。一个在线实例不等于一个空闲执行槽；现有心跳只报告角色和时间，不报告忙闲槽位。
3. 截图中的糖心 H5：21:02:13 创建，开始时间始终为空，21:14:53 取消，实际等待约 12 分 40 秒。同默认队列另一 H5 Main Run 从 21:02:55 执行至 21:20:12，覆盖截图和取消时刻。默认队列长任务占槽与这一等待事实相符；当前环境值不是历史配置备份，不能据此单独证明截图当时的环境变量未变化。
4. 同日晚间另有 H5 实际等待 24.52、24.43 分钟，App 18.07 分钟；独立 Web 队列有一条等待 85.51 分钟。均从持久化初始 Main Run 创建/开始时间计算，没有用任务年龄冒充排队时间。
5. 本轮读取时默认/Web Redis 队列均为空，设备和 App 执行租约没有活动占用，云手机配置 5 个槽位。历史 Redis 深度和设备健康没有快照，不能把当前空队列、可用设备回填成当时状态。PG 历史注册设备数量也不等于当前配置容量。

## 平台代码修复

- 任务详情为 App/H5 注入默认队列读侧，Web 继续使用专属队列；位置来自对应 Redis 队列 `LPOS + 1`，前方数量为真实位置减一。
- 删除数据库中按全平台任务优先级和创建时间推算位置的 COUNT。该排序既不等于实际 FIFO，也把 Web 和 App/H5 混在一起；数据库根任务状态保持权威事实，队列观测不能伪造 `running`。
- 在线适配 Worker 根据对应 `explorer` / `web_explorer` 角色读取。保留现有字段，不新增容量字段，不将心跳数解释为可用槽位。
- Redis 故障、没有在当前队列中找到 Run、未配置观测读侧时保持位置未知，不回退成假位置；任务状态和详情仍能读取。只读观测总时间上限 1 秒，并在异常/超时后取消同批观测请求。
- 已入队与立即执行分开说明：等待适配 Worker 上线或释放执行槽后领取。位置暂不可确认时提示等待调度状态同步。开始操作仍复用原有幂等唤醒，不插队、不直接改成执行中。

## 容量参数与受控部署边界

生产模板 `infra/env/.env.production.example` 原本已有默认并发 4，Web 并发 1；本轮只补充队列和槽位含义，未重复改变默认值。当前线上默认值显式覆盖成 1，所以只发布代码或改 Python 默认值不会扩大实际容量。

| 参数 | 真实作用 | 本轮状态 |
| --- | --- | --- |
| `ALIOTH_WORKER_CONCURRENCY` | 单 Worker 进程内 App/H5 共享队列消费槽位 | 当前线上 1；模板现有 4。需按设备库存、模型额度、浏览器内存完成容量评估后，在受控部署中调整 |
| `ALIOTH_WEB_WORKER_CONCURRENCY` | 独立 Web 队列消费槽位，不借用 App/H5 槽位 | 当前线上及模板均为 1。需要 Web 并行时单独验证资源并调整 |
| `ALIOTH_WORKER_ROLES` | 决定实例是否消费 `explorer`、`web_explorer`、`judge` 对应工作 | 容量与角色必须同时匹配，不能用 Judge 心跳冒充探索消费者 |

参数修改需要 Worker 使用新环境重新启动才生效，须在既有运维窗口、无在途执行或完成既有安全排空流程后部署。用户本轮未授权线上重启，因此本次只交付代码、模板说明与可核对证据；容量扩容未执行，不能标记为线上排队吞吐已恢复。扩容后还须实测多任务同时领取、同设备租约隔离、Web/App/H5 各自队列位置以及资源峰值，不能仅凭心跳在线认定并行验收完成。
