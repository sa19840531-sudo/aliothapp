日期：2026-08-27（Asia/Shanghai）

## 1. 执行结论

本轮按用户给出的顺序提交 8 个 `scan_mode=full` 的 H5 V2 任务。Docker 仅执行 restart，没有执行 build；API、worker、PostgreSQL、Redis 均恢复运行。登录使用 `admin` 获取的 token 只保存在调用进程内，未写入文件或日志。

8 个任务最终都进入 `review`，所有 `rule_judge` run 均以 `h5_inspection_work_drained` 结束，说明质检工作项最终排空；但是 8 个 `main` run 全部是 `failed`，其中 6 个为 `incomplete`、2 个为 `error`，没有一个主探索 run 干净成功。

13 个用户指定页型中，跨站点联合实际观察到 11 个，缺少 `activity` 和 `ranking`，原始联合覆盖率为 `11/13 = 84.6%`。当前页型目录 `2026-08-25.v12` 已移除 `ranking`；按“用户目标与现行目录交集”计算为 `11/12 = 91.7%`。`activity` 是现行目录中唯一仍未覆盖的目标页型。

本报告执行以下严格口径：

- 只以实际 Capture/页型评估结果计覆盖，不能用动作的 `expected_next_page_type` 代替真实落点。
- 动作显示 `completed` 但结果仍在原页或落到别的页型，不计目标覆盖。
- “签到、支付、设置都在 profile”作为硬约束：`activity/payment/settings` 的探索链路必须从真实 `profile` Capture 发起并落到相应页型。
- 直接以深链打开 `payment` 只算“观察到该页面”，不算验证了 `profile -> payment` 链路。
- `post_publish` 是额外发现，不纳入用户给出的 13 类分母。

## 8. 修复优先级与验收条件

### P0：profile 专属候选和动作落点真实性

- home/content/video 页面不得生成 activity/payment/settings 专属候选。
- activity/payment/settings 必须以已判定的真实 profile Capture 为 source；直接深链仅记观察，不记 profile 链路成功。
- action completed 后必须比较实际 result page type 与 expected page type；原页无变化或误入其他页型要形成明确 mismatch，不得当作目标已探索。
- 修复 profile 页面视觉坐标过期/错位问题，优先重绑定当前 Capture 中的真实可见目标。

### P1：无收益重试与恢复

- 同一候选跨兄弟目标轮换时也要遵守按候选计数的失败预算，减少重复 Capture 和 AI 调用。
- `VISUAL_SOURCE_ARTIFACT_MISSING/STATE_STALE` 应回到当前稳定 Capture 重新探测，而不是直接令 main run error。
- `h5_frontier_restore_exhausted` 需要保留可解释的部分完成结果，并避免尚有可行入口时提前封闭。

### P1：startup_ad

- 对找不到“跳过”的页面区分倒计时未到、按钮不可见和实际无按钮。
- 在倒计时或广告自动结束后重新观察，再决定 no_progress，避免任务 6 只探索 startup_ad。

### P1：向量知识有效性

- 保留现有仓储接线，增加可复现的 exact/vector 命中测试。
- 验证 embedding 模型、规范化文本和距离阈值一致；修复后应至少在已知别名回归样例产生 vector 或 exact 命中。
- 报告继续分别显示 static/exact/vector，禁止用 lookup attempt 冒充命中。

### P2：运行与审计

- 解释并修正“任务 review 但 main run 全 failed”的状态语义。
- 修复消费用量写入失败，保证 AI 调用、token 和成本审计完整。
- 对多模态超时增加清晰回退与计数，避免长时间静默。
