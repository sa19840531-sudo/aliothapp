# H5 目标对齐与防回退优化方案

## 决策摘要

保留 Task / Run、Explorer / Judge / Probe、Page Graph、Frontier、Publication、EvidenceRequest、SessionCommandGate 和 Completion Gate。优化现有职责之间的调度与交接，不新增第二套浏览器执行器、任务引擎或站点特判。

核心目标是：在冻结预算内，尽量覆盖不同业务页型及其规则关键状态，保存可判定证据，完成有界质检与补证，最终交付结果或明确缺口。截图更多、动作更多、探索结束、进度 100% 都不能单独证明这个目标实现。

本文前半部分保留复盘时的设计与历史事实。经用户授权后，已实施的最小修改、验证和未完成项见文末实施记录；不能把整份设计直接当成已经实现。没有启动新任务、恢复 Worker 或修改历史数据。

## 保留的架构与需要调整的合同

| 保留 | 调整 |
| --- | --- |
| Explorer 负责浏览器业务探索 | 将页型新增与规则关键证据收益置于普通同类扩展之前 |
| Judge 只读不可变证据 | 同一有效输入不重复判；需要补证时给出可执行、可结算目标 |
| Probe / Restoration 负责取证与恢复 | 不能吞掉新业务页面；交接后重新同步现场与 Frontier |
| Page Graph 记录真实状态与动作 | 不把节点存在等同于可恢复或已完成质检 |
| Frontier 保存待探索入口 | 未完成的已知页型目标不能因补采到过就被当作完成 |
| SessionCommandGate 保护命令互斥 | 补上业务目标交接，不将命令互斥误当作完整调度 |
| Publication、InputSet、规则清单与 Gate | 保留幂等、证据合同与正式报告绑定，不靠放宽 Gate 完成 |

## 优化一 先保证不同页型的代表性覆盖

继续使用现有 Frontier 和有界 Scheduler，不再叠加一套打分系统。

建议明确选择顺序：安全清障和不可延期的现场证据优先；其次未完成的已知业务页型；再其次已覆盖页型中的新规则关键状态；最后才是同类页面扩展。恢复距离用于同级择优，不应让便宜的重复观察永久压住另一个页型。

“不可延期”必须由具体规则证据合同支持，例如离开即丢失的操作前后证据，不能让任意 evidence_insufficient 请求自动抢占最高优先级。等待中的新页型入口应有防饥饿保障，但不得覆盖动作风险边界。

同类详情、滚动、支付档位并非全部无价值：它们可能补齐播放、阅读、价格等规则状态。取得合同要求的代表性证据后让出额度；不能为了少访问页面漏掉规则规定的操作序列，也不能为了访问量无限滚动。

目标来源分开处理：用户显式要求的页型是硬目标；当前任务真实发现的入口是待验证目标；规则清单的 target_page_types 是潜在探索方向，不是每个产品都必须有的全部页面。历史任务证明的可达页型用于回归基线与提示，不能硬编码历史 URL、旧账号或旧点击签名。

## 优化二 补采发现新页必须完成受控交接

支付实例对应的最小改进流程：

```text
Probe 实际到达一个业务页
  → 保存原补证 Capture、动作和来源，不改变历史角色
  → 判断该页面是否已有合格探索评估及相应规则发布
  → 原请求完成或有界退出后，将未完成页型目标交给现有 Explorer
  → 仍在该页时先利用现场，不默认 navigate 回源或重新点击入口
  → 在正常探索合同下完成观察、Assessment、幂等 Publication
  → 原目标补证与新页规则分别结算，再决定返回或继续
```

交接必须校验 Task / Run / Epoch、当前会话、逻辑身份、可用画面、低风险及剩余预算。Snapshot 可用证据优先复用；需要普通观察或新的操作前后证据时才采新帧，不能伪造 Capture 角色满足输入合同。

已有状态的恢复帧仍只补原请求，不普通全规则发布；只有新业务状态或尚未发布的合格规则输入才创建一次正常交接。沿用现有 Publication / Work 幂等键和规则输入去重，防止“新页发布 → 补采 → 再发布”的循环。

如果时间不足、身份不可信或规则操作不允许，记录“已到达但未完成质检”的缺口。不能将到过页面自动算作该页规则都覆盖，也不能隐藏这张截图。

## 优化三 页面等待和弹窗处理共同服务探索目标

复用当前 settle、Detector、Assessment 和弹窗能力，统一它们的决定口径：

| 现场状态 | 处理 |
| --- | --- |
| 纯加载、过渡、无业务内容 | 轻量采样后有界等待，取得新画面；不普通全量质检 |
| 可识别正文、局部加载 | 可继续安全探索；仅对已满足合同的规则取证，不必等所有网络空闲 |
| 有活动遮挡 | 最上层新帧普查、安全关闭目标、动作前验签、关闭后复核 |
| 稳定可用但规则缺操作序列 | 不再按“页面还没加载”反复等；转为具体规则补证目标 |

AI 用于不确定的视觉判断和重新发现目标，不承担每次等待轮询。相同 Capture 的重复解析不是新观察；新 Capture 的视觉相似也不保证动态规则证据可复用。

遮挡且无候选时，允许一次受既有剩余额度约束的重新发现，再按可信命中、唯一性及风险校验执行。旧目标失效必须撤销并重建，不盲点旧坐标。明确多层弹窗只清当前层，不以重新打开页面反复复活开屏。确实无安全关闭方式则留下阻断原因，有界结束该分支。

## 优化四 补证按证据收益收敛而非按请求数量反复运行

保留当前现场检查点，但将请求分成：现场不可延期、可可信恢复后延后、条件尚未触发或不可安全执行。可恢复请求不无限阻止新页型，不可延期请求也受检查点剩余额度限制。

兼容请求可共享一次采集，但必须同时满足各自来源、等价、时间序列、操作、副作用与规则合同，分别挂接各自 InputSet。不能只因同一 URL 或同类页面就合并。

以来源状态、所缺证据目标、合同和等价要求去重；没有新证据不重判。同一失败目标的有界尝试不因换 Request ID、Work ID 或重建 Session 重新计数。请求总开销也占 Task 原预算，不能用“每个请求有限”替代“整任务有限”。

例如广告加载失败、登录后状态、真实收银台金额，不能靠对普通页面反复截图补出来。未触发、不可达、风险不允许、预算不足要各自明确，不冒充 confirmed_not_applicable。

## 优化五 用原有预算完成整条链

不提高 200 次调用或 5400 秒等现有上限，也不直接再配一组相互独立的阶段超时。

先消除可证明的重复成本：同一不可变输入的识别与 Judge 复用；同类补证合并；离开新页前完成必要交接；没有证据收益的循环停止。缓存键必须含证据和识别/规则合同版本，不能以 URL 或页型为键。

时间从本次任务的权威执行起点冻结，探索、检查点、恢复、补采、模型调用、Publication 排空、规则结算、报告生成与清理均传递剩余期限。新 Run 或 Session 不重置已用时间；重启只能恢复原任务剩余额度。

在总预算内预留收尾空间，接近收尾边界后停止新增探索和补证。预留量根据实际已有工作与必要清理成本保守估计，不在此凭空规定比例。循环以真实单调时钟计时，数据库调用和模型耗时也要算进去。

调用前检查任务范围已用量，并将进行中的调用计入许可；并发消费者需要沿用 PostgreSQL 权威控制落实预约/释放，不能“读旧总数后各自调用”。这一落点需在实施前核实最小存储改动，不新增预算服务，不承诺无需迁移就能严格原子控制。Token 缺失时不伪造用量；调用数上限仍可执行。

进展分两类：等待、清障、恢复属于运行进展；新增合格页型、关键状态或满足缺证属于业务进展。运行进展不能无限重置业务无收益计数。截止后有界清理，异常保留可恢复账本，不用无时限 gather 或收尾重试拖住任务。

## 最终交付口径

一个任务可以有限结束但仍有质量缺口。报告至少分开：

- 运行是否结束，资源是否排空。
- 发现的页型、实际到达的页型、合格评估的页型，以及未完成目标。
- 规则清单、已调用规则、有效结论、证据不足、待复核和未执行。
- 通过、失败、已确认不适用，不能把“没访问到”算不适用。
- 正式报告是否满足 Gate 并绑定；预算耗尽的部分结果明确标记。

若需要执行进度最终达到 100%，应表达“运行和结果结算完成”，与通过率、平台成功率、规则覆盖率分开。现有前端百分比不能靠改库或放宽 Gate 强行置满；口径变更单独讨论，不混进导航修复。

## 防回退基线与实施顺序

| 顺序 | 最小交付范围 | 必须验证 |
| --- | --- | --- |
| 1 | 固定两项历史证据与目标清单，复现交接缺口 | 补采真实到支付页且入口已发现，普通支付规则不能默默消失；保留旧任务 6 条候选规则及各自证据合同 |
| 2 | 有限收尾与检查点让路，正常探索防饥饿 | 下游慢或无法恢复时，总时限内终止并给出缺口；主流程不能一直只做恢复/补采 |
| 3 | 新页型交接与同类收益排序 | 补采新页能安全进入 Assessment / Publication；同状态恢复不递归发布；无需重新点击已到达的页面 |
| 4 | 等待、清障、重复识别及补证复用 | 慢加载可用、局部加载可用、多层与异步弹层可清；无可信目标安全终止；动态规则不被错误缓存 |
| 5 | 经用户批准后一次代表性真实验证 | 同配置、冻结代码版本；支付页覆盖不退、规则链可解释、资源排空、报告绑定或明确未满足 Gate 的原因 |

每一项先有失败复现，再作小范围改动和相关回归；整体在批准的真实验收中判定，不让每个小补丁触发六产品重跑。旧证据离线复核不能代替修复后真实业务验收。

基本不回退项：既有底栏到各业务分支、列表与详情有效取证、个人中心到会员页、多层弹窗关闭、滚动容器定位、补证来源等价、外链/风险边界、输入挂接、Publication 幂等与 Gate 完整性。页型数提高不能抵消其中关键路径丢失。

实施期间只处理这些合同问题；新增特殊站点、另写探索引擎、扩大产品批次、无限提高预算均不在范围内。基线失败就停止扩大验证，定位该次改动，不在未收口版本上继续叠修。

## 2026-10-09 实施记录

本轮处理完整复盘的六个问题域，不以两项支付样本代替整体复盘。没有新增任务引擎、站点配置或预算服务，没有数据库迁移。共享 Worker 仅原生 `TaskTarget.platform=h5` 且 `workflow_version=v2` 分支采用新的期限；App/Web 的既有等待与消费路径保持不变。

| 问题域 | 本轮落实 | 验证与边界 |
| --- | --- | --- |
| 加载临时态 | 保留既有有界重观察、视觉与结构可用性判定；不把 loading、partially_loaded 或空候选升级为覆盖。每个新 Capture 重新识别，重复观察同一不可变帧才复用 | 真实 Chromium 慢启动不重载；正文加载中仅允许独立验签导航；未验证所有外部产品的加载时长 |
| 页型而非页面数量 | 当前页必要清障、详情取证、横向取证与返回仍保留原优先级；其余候选中优先未覆盖的安全业务页型，再按既有位置、风险与采样排序 | 新页型优先于更多同类列表样本，包含跨来源候选；旧详情返回和支付横向取证回归保留。没有改变 max_pages 含义或虚报规则覆盖 |
| 通用弹窗 | 活动遮挡没有安全候选时，复用既有最多三次能力重观察，重新取得现场普查与签名；达到上限保留阻断原因 | 多层、异步换层、无效外侧点击、无文本关闭键及无可信目标拒绝；不增加任意坐标点击或验证码绕过 |
| 探索与补采交接 | 页面检查点补齐覆盖权威对账。可信 Probe 新业务页首次到达时，保留原 selected 目标为 pending，先做一次普通 OBSERVE，再接回原探索 | 同任务、同会话、最新帧、稳定可评估、域名与路线、动作与时限、页型采样策略全部检查；补采帧仍为 evidence_only，新观察走普通 after_action 合同。不承诺所有已知页型的新规则状态已被自动交接 |
| 预算与无收益循环 | 同一 Task 汇总全部 Run 的真实模型流水；启动、探索及关闭后补采检查沿用原调用/Token 上限；检测缓存最多 64 项且不跨 Run。Probe/补采返回“尝试过”不再重置无进展计时 | 审计落库失败仍拒绝放行；新帧、另一 Run、失败持久化不借用缓存；尝试无新证据会有限退出。尚无跨进程物理调用原子预占，不能保证预算边界没有并发或单批次超调 |
| 有限收尾 | Runtime 从原 started_at 冻结期限，重试等待与补采不刷新期限；慢 Judge 跨期限后不启动 Probe。关闭后 Snapshot 与页面/聚合等待只使用剩余时间，计入读库耗时；冻结与会话关闭各设有限清理窗口 | 过期不新建会话、不领取探索、不新开 Snapshot 重判；允许原门禁按缺证或失败结算，不强改成功。挂起关闭必须失败。依赖协程合作取消，不能宣称不可取消的驱动或所有报告/数据库调用均已获得硬终止保证 |

新增失败复现及边界用例集中在 `services/api/tests/test_h5_goal_alignment.py`。旧回归仅修正真实日期、检查点新增对账顺序和去掉无收益 continue 后的调用次数，不删除安全断言。

验证记录：补充预算启动、交接拒绝及 App/Web 分支隔离边界后，非浏览器 H5 与 Worker 组最终 2524 通过、2 跳过（53.07 秒）；两项 PostgreSQL 集成测试因未配置隔离的 ALIOTH_TEST_DATABASE_URL 跳过。真实 Chromium 加载/弹窗/滚动及观察组 232 通过（342.51 秒）。两组有交叉用例，不累加成独立总数。未启用原库或隔离数据库集成验收，未运行历史六产品批次，也未重启服务加载本轮代码。

### 明确保留的后续验证

- 同页型但新规则关键状态的交接，必须证明新的规则收益和原 InputSet 绑定；本轮只交接可信首次业务页型，不能按截图差异递归发布。
- 严格跨进程模型许可需在既有 PostgreSQL 控制内原子覆盖审计与在途调用。Task 汇总是计量修正，不是这项许可的替代；不为压费用抬高预算或伪造缺失 Token。
- 正式报告、Completion Gate 和资源排空仍需一次经授权的代表性真实任务验证。局部测试通过不能保证所有页型、规则和外部站点都达到 100%。
