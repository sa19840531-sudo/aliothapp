# 质检持久化工作项协议

## 目标与边界

Alioth V1 保持单 Main Agent 和分层单体架构，通过 PostgreSQL
持久化页面探索与规则质检之间的待办协议。页面探索负责产生页面采集、证据和候选规则；
持久化调度器按租约领取规则批次；Judge 只消费可信 Observation Packet；最终结果仍写入
`qc_rule_execution`。

本协议只解决质检控制面持久化，不同时改变证据对象存储策略，也不尝试序列化或跨进程
恢复浏览器会话。

## 事实源

- `qc_inspection_work_item` 是规则批次是否待执行的唯一事实源。
- `qc_inspection_work_item_rule` 保存批次预期规则集合、契约哈希和正式写回关联。
- `qc_inspection_attempt` 保存可恢复的 Judge 输出以及重试审计。
- `qc_observation_packet` 继续作为 Judge 的标准证据输入。
- `qc_rule_execution` 继续作为规则最终结果。
- `WorkingMemory`、`qc_page_capture.inspection_*` 和 `qc_task_page_node` 是执行缓存或展示投影，
  不得反向覆盖持久化工作项事实。
- 截图、DOM、HAR、控制台日志和 Base64 不得写入工作项；工作项只引用页面、规则、证据包
  和规则执行 ID。

## 工作项粒度与幂等

一个工作项对应 `candidate_rules_tool.execution_plan.batches` 中的一个批次，稳定身份为：

```text
task_id + page_capture_id + batch_key + input_hash
```

`input_hash` 必须覆盖协议版本、页面采集、锁定规则集版本/快照、批次路由以及有序规则
契约哈希。相同输入重复发布返回同一工作项；任何影响判定的规则契约变化都会产生不同哈希，
消费方不得静默使用新规则替换旧输入。
单批规则超过运行时 Judge 上限时，生产侧必须按相同顺序切成最多 20 条的确定性子批，
并在 `batch_key` 增加 `:chunk:N`；领取时页面采集与当前未完成规则编码集合必须完全匹配，
禁止跨策略、类别或会话依赖混领。

工作项还必须区分 `control_mode=shadow|enforced`。Shadow 工作项只用于双写和对账，
不得被调度器领取，也不得进入报告完成门禁；Enforced 工作项才是正式调度事实。
同一批次从 Shadow 切换到 Enforced 时必须生成独立身份，禁止复用未收口的影子行。

`producer_agent_run_id` 记录探索生产者，`consumer_agent_run_id` 记录实际质检者；
二者不得合并成一个永久所有者。`active_session` 额外绑定 `session_owner_agent_run_id`。

## 状态机与租约

工作项主路径：

```text
pending -> leased -> running -> succeeded | partial | failed
running -> retry_wait -> leased
running -> waiting_evidence -> pending
任意未完成状态 -> cancelled | superseded
```

- `leased/running` 必须同时存在 lease owner、lease token、过期时间和 consumer run。
- 领取必须使用 `FOR UPDATE SKIP LOCKED`，过期租约可在最大尝试次数内回收。
- 状态更新必须同时校验当前状态、lease token 和 `row_version`。
- 只有 `retry_wait` 可以设置未来的 `next_attempt_at`。
- `snapshot` 可由兼容的新 Run 恢复；`active_session` 只能由会话所有者执行。
- `active_session` 会话丢失时必须以 `INSPECTION_ACTIVE_SESSION_LOST` 失败关闭并进入
  人工复核，禁止基于旧会话证据盲目重试；已有正式规则结果仍可在最终门禁安全对账。
- 长 Judge 调用按租约三分之一周期续租；续租与终态推进共享 `row_version`，旧消费者不能
  在租约失效后覆盖新消费者。

## Judge 交接与恢复

Judge 调用前创建 `qc_inspection_attempt`。Judge 成功后先把有界结构化输出写为 `judged`，
再写 `qc_rule_execution`，最后把 Attempt 标为 `written`。

因此必须覆盖以下恢复点：

1. 已领取但未 Judge：租约到期重新领取。
2. 已 Judge 但未写规则结果：从 Attempt 重放写回，不再次请求模型。
3. 已写规则结果但工作项未收口：根据 `qc_rule_execution` 对账完成。
4. 部分批次成功：保留已写结果，只重试未完成成员。

V1 不增加独立微服务：同一 Worker 内由业务中间件在结构化 Judge/写回前领取完全匹配的
工作项；Main Agent 收口后，Worker 再排空可跨会话恢复的 `snapshot` 工作项。后者优先
同步已有 `qc_rule_execution`，其次重放旧 Attempt，只有二者都不存在才再次调用 Judge。
`active_session` 仍必须在浏览器会话存活且 Run 所有者一致时即时消费。

生产计划、运行时调度和持久化认领必须共用同一批次身份算法：

- `rule_engine` 只按 `strategy + session_dependency` 合批，持久化 `category=null`，
  `batch_key` 使用 `rule_engine:all:{session_dependency}`；确定性规则共享本地证据读取和
  批量写回，不得按业务类别拆散。
- `llm/hybrid` 按 `strategy + category + session_dependency` 分批，确保每批只加载对应
  类别的能力 Skill。
- 三条链路不得各自拼接批次键；任一批次的规则顺序和最多 20 条的分块边界也必须一致，
  否则 Judge 精确认领必须失败，禁止回退到内存态绕过。

## 启用策略

持久化工作项门禁与异步唤醒消费**始终启用**，不设运行时开关（2026-08-04 起移除
`ALIOTH_QC_INSPECTION_WORK_ITEMS_MODE` 与 `ALIOTH_QC_INSPECTION_WAKEUP_MODE`，
Shadow 对账链路一并下线）：

- 候选规则返回即幂等发布 Enforced 工作项，发布失败必须阻止该批次在内存中被视为已建立。
- Judge、规则写回与报告 Tool 都必须通过 Enforced 工作项门禁，禁止绕过租约直接执行；
  找不到精确匹配工作项时返回可重试阻断，不得回退到 WorkingMemory 作为事实源。
- Worker 同时运行异步唤醒消费（Outbox → Redis Stream → claim），与工具内联消费争抢
  同一批工作项时以租约裁决，先到先得，重复唤醒幂等。

## 完成门禁

任务报告发布前必须同时满足：

- 动态探索没有待执行动作；
- 没有未完成或过期未回收的持久化工作项；
- 每个工作项规则成员均有正式规则结果或明确失败/人工复核终态；
- 没有仍在运行的页面后台判定协程。

普通预算、卡死、页面不完整和工作项不完整进入 review/incomplete；基础设施或模型全局故障
进入 failed/error。任何终止路径都不得因为报告已生成而伪装为完成。
Worker 在正式报告前先用已有规则结果恢复工作项；仍缺少正式结果的成员统一记录错误并把
工作项置为 `failed`，同时把 Run 转为 `incomplete/needs_review`。只有确认不存在任何
Enforced 非终态工作后才允许生成最终报告。

## 查询投影与观测

工作台通过
`GET /api/v1/workstation/tasks/{task_id}/inspection-work-items`
读取工作项、规则成员与 Attempt 的只读投影，可按 `control_mode=shadow|enforced` 筛选。
响应必须包含工作项/成员/Attempt 状态计数、Enforced 非终态数以及
`active_session` 会话丢失数；Attempt 只暴露是否存在持久化结果，不返回 Judge 正文或原始
证据。最终报告的 `run_observability.inspection_work_items` 同步记录领取、完成、恢复、延迟、
门禁失败和废弃 Attempt 数，并嵌入报告生成时的持久化状态计数快照。领取/完成总量必须以
Attempt 和工作项终态快照补齐，不能只统计 Main Agent 退出后的 Snapshot drain，否则即时
消费全部成功的 Run 会被错误显示为 0。
