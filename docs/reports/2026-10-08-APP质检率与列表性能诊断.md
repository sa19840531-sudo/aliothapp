# APP 质检率与任务、报告列表性能诊断

2026-10-08 对用户指定的[黑料网 app 报告](http://192.46.230.40/admin/reports/97ae1d9c-ebb3-46cb-80f0-491f449c05bc)进行线上数据库只读核验。任务 ID：`97ae1d9c-ebb3-46cb-80f0-491f449c05bc`。本文区分线上事实、本地修复和独立进程候选验证，未部署或修改历史任务。

## 质检率公式和实际统计错误

报告下方每期、每规则的质检率为：

`已有记录中得出结论的次数（通过 + 未通过 + 真实不适用） / 已有执行记录总次数 × 100%`。

它不等于通过率，也不等于全部所选规则的覆盖率。顶部瓦片按唯一规则归并，下方质检率按执行次数计算，同一条规则可能在多个页面执行。

线上本任务有 343 次执行，涉及 20 条唯一规则；所选规则集冻结总数为 73。原读模型把 61 次通过和 282 次跳过全部当作有效结论，得到 100%。其中 263 次明确记录 `SUPPLEMENTAL_EVIDENCE_DISABLED`，结构化结论为 `evidence_insufficient`，说明证据不足且自动补采关闭。把这些记录读成“不适用”属于统计错误。

仅在独立诊断进程加载修复后的共享分类和原因 SQL，对同一线上任务重新读取，得到：

| 逐次结果 | 原展示 | 修复后投影 |
| --- | ---: | ---: |
| 通过 | 61 | 61 |
| 真实不适用 | 282 | 19 |
| 证据不足，归“其他” | 0 | 263 |
| 质检率 | 100% | 23.3% |

修复后质检率为 `(61 + 19) / 343 = 23.3%`。通过率在已有通过/未通过的结论中仍为 100%，不能据此说明其余检查已完成。

按唯一规则归并时仍保留“其他优先于通过”的既有口径：16 条规则至少有一次缺证，3 条归通过，1 条归不适用；不是简单地保留“11 条通过、9 条不适用”。同一规则在一页通过、另一页缺证时，整体仍有检测缺口。详见[只读新旧投影](assets/2026-10-08-app-qc-list-performance/report-projection.json)。

## 另外 53 条为何没有记录

本任务检查范围为首页、内容列表、内容详情、视频列表、视频详情五类。当前 73 条启用规则均没有在任务开始后更新，分类与运行记录对账如下：

| 无记录原因 | 条数 | 依据 |
| --- | ---: | --- |
| 不支持 APP | 2 | 规则目标端仅 WEB，或 WEB/H5 |
| 只适用本次检查范围之外的页型 | 13 | 例如充值、个人中心、设置、帖子发布等 |
| 要求登录，未获得登录事实 | 4 | 用户输入防刷、评论发布、互动状态、播放历史恢复；Capture 的 `session_auth` 均未记录 |
| 快照质检阶段未执行 | 31 | 候选执行路由为 `snapshot`，没有执行记录 |
| 任务聚合阶段未执行 | 3 | 弹窗连续展示、官方群入口、Toast 样式；没有聚合候选/结果 |
| 合计 | 53 | 加已有记录的 20 条等于 73 |

20/73 = 27.4% 只表示有记录规则占所选规则集总数的比例，其中还包含证据不足记录；不能称为本次适用范围的完成率。

旧展示的六类结果只对已有记录的规则归并，因此原截图为 `20 = 9 + 11 + 0 + 0 + 0 + 0`。`73 = 20 + 53`只能解释旧数字，不能证明全部规则已应用。旧流程先按平台、页型、认证筛候选，被过滤的规则没有逐条处置台账；规则总数虽冻结，完整执行契约与应用清单没有冻结。快照与任务聚合阶段未完成又留下34条缺口。这是用户指出的核心问题，不能只增加“无执行记录53”的说明就视为修复。

运行证据显示第39轮探索成功，第40轮探索 Work 保留 `running`。北京时间10月7日11:42:11，任务已经进入 `review / needs_review / sealed`，主 Run 为 `done / sealed_for_review`；完成门禁未通过，原因 `manual_review_seal`，`exploration_terminal=false`、`app_coverage_satisfied=false`，业务质量 `unknown`。

11:42:25在途探索 Work 续租被数据库“任务已进入最终封存阶段，拒绝晚到V2写入”拒绝，随后才出现 `AppExplorationLeaseLostError`；取消工作项也被同门禁拒绝并回滚。因此租约丢失是封存后的结果，不能作为最初中断原因。后续收口补视觉事实出现 `AppVisualObservationPersistenceError`，11:43:04规则兜底补记再次被已封存门禁拒绝，未形成封存 Evidence Index、探索 Result 或 App Inspection Publication。已有页面质检均为 `active_session`，快照及任务聚合链路没有完成。技术异常封存保护在该线上版本已存在且被调用，不能将它归因于未发布修复。

进一步核对发现，这份提前封存快照不符合当前部署的正式 Completion Gate 构造合同：`manual_review_seal`不属于正式原因枚举，存储原因与事实派生原因不同，`facts_hash`和快照ID均无法通过线上正式构造器复算。API、Worker镜像代码及数据库存储函数中未找到对应标记。现有日志证明提前封存打断了在途探索，但未提供封存调用及操作者的明确记录，SQL成功语句审计也未开启；来源与操作者仍无法确认，不据此推断人工、运维或直接SQL操作，也不能将后续视觉异常倒推为封存起因。保留晚到写入和封存保护，不绕过门禁补写历史。详见[分类和门禁事实](assets/2026-10-08-app-qc-list-performance/scope-diagnosis.json)、[封存时间线](assets/2026-10-08-app-qc-list-performance/seal-timeline.json)。

本轮未重跑任务、开启补采、补造缺失结论或改写历史封存。

## 全部73条规则的应用闭环

新 APP V2 完整质检任务在提交事务中，先冻结所选规则集的全部启用规则、完整判定契约和逐条适用性判断，再创建任务及主 Run；事务失败一起回滚，幂等提交沿用原清单。页级候选、判定定义、判定写入策略和聚合规则消费同一冻结契约，后续修改或禁用规则不漂移本次任务。没有增加数据库表或迁移。

每条规则都必须有明确处置：平台或渠道明确不支持时说明不适用依据；适用页型不在用户选择范围时单列范围外，不冒充产品不适用；缺登录事实、未取得页面证据、未执行和异常保留缺口。适用规则继续通过现有页面、快照及聚合流程执行，完整清单不会自动扩大勾选范围或制造执行记录。

完成门禁对全部范围内规则核对当前主 Run、收口轮次与真实执行，独立 Judge 只能通过当前 Capture 或精确聚合 Work 关联补齐。某规则一页通过、另一页缺证时仍阻断完成；被当前结论替代的启动占位保持原语义，遮挡缺口只由同页型结论替代。损坏清单、旧 Run、旧轮次和未执行均不能放行。封存复核仍可保留部分成果，但不代表全部质检完成。

成功正式封存会将任务阶段轮次提升一次，业务证据仍属于封存前轮次。读侧仅在同任务、同当前轮次且门禁通过的权威快照绑定下读取前一证据轮次，分别保留任务阶段与证据阶段；失败封存和错误绑定不能据此借用旧证据。聚合候选总量同样读取冻结清单，运行中新增或启用别的规则不会扩大本次门禁分母。

报告和任务详情逐条展示完整规则清单和原因，复用现有整体检查入口；无执行项的 `execution_id=null`，不冒充AI判定、不参与执行质检率，也不能人工确认补造结论。真实执行次数和实际使用规则数单独保留，任务执行统计不会从343膨胀成396。六类结果现在对完整清单互斥归并，其合计为规则总数，不再局限于旧页面中的20条。合法空清单表示无可检规则，适用性核对可结束，但不生成100%的质检率。

历史任务只在规则数量完整、规则与组合规则集自任务创建后均未修改时只读重建清单，标记 `legacy_verified`；无法核实则明确清单不可验证，不猜测当时规则，不改写历史任务。在同一线上只读快照中加载本地候选模块，实际得到：

真实执行仍为343次、实际使用20条、补充53条无执行清单项；执行质检率仍为23.3%，范围内未完成54条，`rule_inventory_complete=false`。该验证仅在独立进程内读取，没有部署替换服务或写入业务数据。详见[全规则只读投影](assets/2026-10-08-app-qc-list-performance/full-rule-inventory-projection.json)。

## 列表接口性能

用户截图：任务第一页 20 条耗时 6.38 秒，报告第一页 10 条耗时 12.52 秒。原截图保存在[报告汇总](assets/2026-10-08-app-qc-list-performance/user-report-summary.png)、[任务接口耗时](assets/2026-10-08-app-qc-list-performance/user-task-timing.png)、[报告接口耗时](assets/2026-10-08-app-qc-list-performance/user-report-timing.png)。当前数据库有 93 个未删除任务。

线上部署的列表仓储代码尚无本地 HEAD 已有的只读事务 `SET LOCAL jit=off` 修复。在同一只读快照内对线上原查询各执行一次，定位到主要等待发生在数据库即时编译（JIT）：

| 线上原查询 | 开启 JIT 的 SQL 执行时间 | 其中编译时间 | 关闭 JIT 的 SQL 执行时间 |
| --- | ---: | ---: | ---: |
| 任务列表 | 6,235 ms | 5,780 ms（92.7%） | 424 ms |
| 报告列表 | 11,728 ms | 10,499 ms（89.5%） | 1,224 ms |

使用该任务提交者当前数据库权限（平台管理员，可读全部任务），线上原服务层三次实测任务列表为 5.87–6.24 秒、报告列表为 12.31–12.44 秒；用户信息读取约 2 ms，序列化不足 1 ms，复现了与截图相近的等待。该测试不是原截图账号的 HTTP 验收。JIT 关闭在开启之后测量，缓存条件存在差异；保留缓冲区读取数据，主要慢因以实际编译时间为证据。既有修复仅在列表只读事务内关闭 JIT，事务结束恢复设置，不修改数据库全局配置。

本次进一步定位到分页前逐任务规则计数和重复占位替代扫描；报告分支 HEAD 旧计划的替代子查询执行约 7,605 次、命中约 46 万缓冲区。

修复将完整规则统计移到分页之后，并按当前页任务批量建立结论集合；分页前的报告状态筛选保留所需的有效规则存在性判断。公司、部门、本人范围，当前 Run/H5 owner，正式报告绑定与取消状态均保留。`report_list_meta` 实测约 8–11 毫秒，本轮没有无依据地改写它。

在同一线上只读快照、相同统计助手版本和关闭 JIT 的条件下，将本地 HEAD 原查询与本次候选查询进行 31 组完整返回字段对账，包含权限、端类型、状态、页码和筛选条件，差异为零。热缓存各测三次的中位数如下：

| 核心查询 | 本地 HEAD 原实现 | 本次候选实现 | 降幅 |
| --- | ---: | ---: | ---: |
| 任务列表 | 436 ms | 372 ms | 14.6% |
| 报告列表 | 1,157 ms | 270 ms | 76.7% |

报告查询缓冲区命中约 46.3 万次降至 9.7 万次。以上为 SQL 时间，不能代替实际 HTTP、鉴权、网络和浏览器整页时间，且线上服务尚未更新。需要一起发布仓库已有 JIT 隔离修复和本次批量统计优化，再以实际账号确认接口耗时。详见[性能对账与计划证据](assets/2026-10-08-app-qc-list-performance/list-performance.json)。
