# 页面类型覆盖率优化实施计划

> 日期：2026-07-25
> 范围：页面探索、覆盖统计、执行调度、回归验证与质检报告

## 目标

在不伪造瞬态页面、不放开交易或提交动作的前提下，提高自动探索对业务页面类型的到达能力，并将结果拆分为可解释、可审计的双轨指标：

1. 业务页面覆盖率：按产品实际适用的稳定业务页面类型统计，目标约 80%。
2. 探索完整度：按已发现的安全可达入口和动作终态统计，目标不低于 90%。
3. 平台能力覆盖：通过受控样本验证 14 种页面类型的识别能力，不与单一产品业务覆盖混算。
4. `line_loading` 仅在严格证据成立时计入；业务页播放器等局部加载只记录为 `loading_state_observed`。

## 实施步骤

### 1. 补齐安全导航语义

- 为 `ranking`、`settings`、`post_publish` 增加统一导航别名。
- 允许只负责打开编辑器的发布入口作为低风险导航候选。
- 保持“发布、提交、支付、充值、购买”等真实提交动作高风险，不自动执行。
- 先增加失败测试，再做最小实现。

### 2. 增加双轨覆盖统计

- 在页面探索汇总中保留 `page_state` 和页面类型证据。
- 输出已观测类型、稳定业务类型、生命周期瞬态类型、缺失类型。
- 输出安全动作的已发现、已执行、已完成、阻断和未终态数量。
- 对无法从证据确定的“产品适用类型总数”返回未知状态，不用 14 作为分母制造虚高或虚低。
- `line_loading` 只接受严格分类结果；普通 `loading` 进入局部加载观测。

### 3. 覆盖优先与自动回补

- 在规则执行不丢失的前提下，为缺失类型的低风险导航提供覆盖优先级。
- 当前页规则完成后，优先执行能补齐缺失类型的安全动作。
- 对超时、阻断、无法执行的动作写入终态与原因，避免队列反复空转。
- 支持首轮结束后的安全回补，并限制深度、次数与风险等级。

### 4. 回归验证

- 运行页面导航别名、页面检测、探索记忆和探索汇总的定向测试。
- 运行相关服务测试集，检查已有页面识别与规则调度无回归。
- 进行独立代码审核，修复确认的问题后再次测试。

### 5. 本地完整链路质检

- 逐个验证 23 个目标 URL 的可访问性，并记录证书、超时、重定向和响应状态。
- Docker 仅重启，不执行 build。
- 先单 worker 验证完整链路与可观测性。
- 稳定后使用 3 至 5 个 worker 执行全部 URL。
- 核查向量库检索是否参与页面探索，记录 worker 执行效果、探索页面、命中页面类型和执行规则。
- 对影响探索的可复现阻断继续修复并回归。

### 6. 交付报告

- 输出 HTML 质检报告。
- 明确区分业务覆盖、探索完整度、平台能力和不可达/不适用类型。
- 列出每个站点的可访问性、任务状态、页面证据、规则执行、向量检索证据、阻断和修复结果。
- 给出是否达到约 80% 业务页面覆盖的结论及剩余风险。

## 验收约束

- 不把已经识别为其他业务类型的页面自动改记为 `line_loading`。
- 可以记录“曾观察到加载状态”，但该事实不增加 `line_loading` 类型覆盖。
- 不自动执行发布提交、支付、充值、购买、删除、退出登录等高风险动作。
- 不通过修改分母或无证据推断来制造覆盖率。
- Docker 验证阶段禁止 build。
