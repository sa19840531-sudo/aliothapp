# Web 七站主线、登录支线和长图证据实测（2026-09-28）

本轮在 `codex/web-evidence-recovery` 的隔离 worktree 中使用生产 `WebDesktopCapturePolicyBrowser`、`WebLoginBranch` 和 `WebLoginSessionBrowser` 做浏览器侧实测。证据仅写入本机可视化目录 `C:/Users/p/.codex/visualizations/2026/09/21/01a0c3fd-ad6f-75c0-a72e-fe4c990dd602/web-seven-flow-20260928-r1`，未写远程数据库，也未修改站点配置。没有执行注册、充值提交或付款。

每站过程如下：

1. 用独立主会话打开首页，清理遮挡，保存 ready 视口截图和 DOM。
2. 按生产补采请求 `web_full_page_supplemental` 采集首页；保存原始 PNG、尺寸、字节数、SHA-256、滚动覆盖清单，并按生产 PNG 合同和来源 URL 校验。
3. 遍历冻结 Catalog 中的可执行同源入口；chigua 无冻结 Catalog 条目，改用首页生产导航候选。每个入口独立导航、清障、保存视口截图与 DOM；首个成功菜单再做一次补充长图采样。站外跳转另记终态，不当作同源页面成功。
4. 回到主会话首页，记录原 Context／页面对象和认证类 Cookie 签名是否变化。随后在独立 Browser Context 执行白名单登录、账户复核及仅导航的充值入口检查；未知跨源请求继续拦截。
5. 登录支线结束后再次读取主会话身份、认证 Cookie 状态、截图和 DOM，验证支线成功或失败都不破坏主线会话。

“补采成功”只表示 PNG 与来源身份满足生产截图合同，并且本地文件已保存。`web_direct_full_page` 才是一张整页长图；`web_scrolled_viewport` 是滚动到指定位置后的单张视口图，需结合 `page_coverage` 清单理解，不能称为整页长图。质检的内容正确性未由本轮脚本判定。

正式 Worker→数据库证据入库→质检链路在本机不可运行：Docker Desktop 的 WSL 引擎启动失败，本地 API 探测超时。下文的主线结果是生产浏览器采集器的逐页实测，不等于正式任务完成或质检通过；新任务默认 `menu_limit=10` 也未在本轮改变。

本轮相关回归：`test_web_full_page_supplemental_capture.py`、`test_web_full_page_long_document.py`、`test_web_runtime_stage_login.py` 和 `test_web_runtime_stage_effects.py` 共 149 项通过。

## 长图与证据

七站首页及每站首个成功菜单都调用了生产 `web_full_page_supplemental` 补采请求。黄果爱、黑料、hl365、chigua、avhub360、91jav1 的首页与菜单共 12 次补采被接受，均生成 `web_scrolled_viewport` PNG 和 `web-scrolled-viewport-manifest.v1` 清单。所有这 12 张图实际尺寸均为 1920×1080，页面先滚动至约 1,920px（接近文档底部时取可达最大值），采集后恢复原位置；PNG 格式合同、来源页面身份与本地文件检查通过。它们只能证明相应视口被留存，**不是整页长图，也不覆盖整个页面**。例如 hl365 首页文档约 18,673px，清单仅标注 1,920–3,000px 的视口范围。

91porna 首页在首次和被动等待 25 秒后的清障尝试中仍得到 `WEB_LOGIN_OBSTRUCTION_LIMIT`，因此没有首页补采。它的菜单滚动视口图与覆盖清单文件虽已写到诊断目录，但补采结果是 `WEB_FULL_PAGE_SCREENSHOT_STATE_DRIFT`：前后页面状态或身份一致性未获证明，生产校验拒收，不能作为有效长图证据。诊断输出中的可见 URL 相同，不能据此断言是地址变化。全轮没有一张图片的 `purpose` 是 `web_direct_full_page`。回退探测的常见原因是未加载完的图片、内层滚动容器或扫描上限；例如黑料首页图片待加载数为 0，但仍有 1 个内层滚动容器，故也未直接调用整页截图路径。现有探测把 `overflow:hidden` 容器纳入计数，可能过于保守，需单独评估，不能仅凭此次观察放宽。

首页 ready 视口截图和 DOM 与补采附件分开保存。质检是否认可页面内容没有在这轮浏览器侧实测中执行，`补采成功` 只表示截图合同和页面身份检查通过。

## 主线与支线隔离核查

登录前记录主线 Browser Context、Page、URL 和认证类 Cookie 签名；登录在新的 Context 中运行，关闭后重复读取，并再次采集主线首页。七站均能在支线结束后继续得到主线截图和 DOM，且 Context、Page、URL 未改变；六站 Cookie 签名也未改变。黑料唯一的 Cookie 签名差异经无凭据对照复测：主会话打开后空等 25 秒，`__web_sdk_sid_v1` 签名已经自行变化；随后新建和关闭空白隔离 Context，主会话 Cookie 签名不再变化。`session_evidence()` 的正则将名称含 `sid` 的 SDK Cookie 也计入“认证类”签名，故原差异不足以证明登录支线污染主会话，也不能单独作为登录成功证明。对照记录在 `heiliao_cookie_control/control.json`。

91porna 的首屏弹窗属于主线自身的遮挡缺口：页面 HTTP 200、截图及 DOM 虽已保存，但清障器未在本轮首页调用内完成。稍后的登录前首页及登录后首页可清障并采集；被动等待只是本轮诊断手段，未改动生产清障逻辑。chigua 的 `/twitter.html` 浏览器导航记 `gap`，只读首跳核实为 HTTP 302 到 `https://x.com`；这是站外跳转，不算同源菜单缺失。
