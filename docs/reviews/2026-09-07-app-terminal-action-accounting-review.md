# App 终态动作计数与恢复审查

日期：2026-09-07。范围：观星第 5 项“有界自由探索”的最后一轮动作计数；不增加截止后的设备操作或视觉分析。

## 问题与修复

已执行动作且已有 After Capture 的轮次，可能因 deadline 到达而同时进入终态。原统计先判断 `is_terminal`，将这次动作漏计；只修改内存计数还不够，进程恢复时原 Work 预算仍可能是本轮执行前的值。

- 动作协调事实先于纯终态标记；纯终态确认、Timed Observation 和原有重试等待语义保持不变。
- 同一轮动作产生的终态保存累计 `consumed_action_count` 与实际结果 Capture 引用。没有本轮动作的纯终态不改写原对象。
- 已生成合法后继但在提交时跨过 deadline，使用该后继已结算预算，不再额外加一次；终态仍绑定父 Work，并使用已经完成的后态评估结果。
- 只捕获明确的截止拒绝，不根据异常正文含有 `deadline` 就吞掉持久化失败。
- 恢复读侧使用现有终态中的累计值；旧格式仍从末端 Work 预算推导。拒绝布尔值、非整数、计数回退、超过锁定上限或一次跳过多轮的载荷。
- Runtime 的恢复校验同步理解末端终态计数，不能读回 `3/3 + 已消费 1` 后又用旧的严格预算等式拒绝恢复。显式计数必须与恢复结果一致；旧格式继续严格校验。恢复已终结的工作不再次派发或重复计数。
- 截止提交竞态结束后重新检查 Work/Frontier 租约及取消状态，避免将此时到达的取消写成预算耗尽。

## 验证

旧实现已由“截止前开始、After 返回后跨截止”的真实 Runner 隔离用例复现：执行一次但计数为零。回归同时覆盖结果接收、终态载荷、恢复重读、正常与异常边界，并使用显式隔离 PostgreSQL 验证终态实际写入后读回。

数据库正例使用“原 Work 已消耗 0，终态已消耗 1”，没有用两个来源都为 1 的样本掩盖旧读侧错误。真实 PG 写入和恢复读取通过；`ProductionAppV2RuntimeExecutor` 的恢复用例验证不再发布、不再执行动作，最终收尾计数仍为 1，结果仍是证据不足而非虚报完成。

取消竞态反例在修复前实际失败：提交时收到专用截止错误后，虽然取消信号已经到达，仍返回 `budget_exhausted`；加入再次复核后返回 `cancelled`，没有写入预算终态。

- 第二批暂存源码独立导出 `/tmp/alioth-app-terminal-index-gg8fwr`，已核对 Python 实际导入该目录。59 文件最终组合 **1886 passed、12 skipped**；覆盖第一批以及 App 终态计数、恢复仓储、Runtime 和真实 PG Checkpoint 的迁移/约束测试。
- 12 项是需显式开启的 CLI 集成，另在同一导出源码启用锁定 CLI 和真实本地浏览器得到 **62 passed（76.59 秒）**。不累加两组数量，也不称为仓库全测。
- 原隔离库有先前封存反例留下的不可变审计数据，导致 Checkpoint 用例回退迁移被保护性拒绝（当时为 1885 passed、1 failed、12 skipped）。没有关闭触发器或强删审计；改用同一 Docker 端口 `127.0.0.1:51309` 的新空库 `alioth_terminal_final_20260907` 与独立配置库 `alioth_terminal_schema_20260907` 后完整通过。
- 三次独立反向注入分别撤销动作优先计数、恢复仓储计数赋值、Runtime 显式计数校验，分别检出 **2、2、1 项失败**。每次只改临时导出，恢复后逐文件比较源码一致，再重新运行完整组合。
- Ruff、白名单暂存审查和差异检查通过。测试技能促使验证延伸到真实保存、重新读取和 Runtime 收尾，不只验证局部函数返回值。
